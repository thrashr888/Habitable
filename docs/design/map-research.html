Habitable · Map research · October 2026

Can real Terraform draw a map?

I measured 3,449 resources from real production repos to find out what the app can actually know about a resource: what kind of thing it is, what it belongs to, and where it sits relative to everything else.

Short answer: yes, with resource types doing most of the work. Name prefixes help, but with a different job than you'd expect. The resource type, looked up in the provider's own docs, tells you what kind of thing something is. Shared name stems tell you which resources are parts of the same thing. References tell you the order. Together they fold a median workspace of 25 resources into 4 tiles.

The corpus

What real configs look like

Production infrastructure from GOV.UK (alphagov), Canada's Digital Service (GC Notify and GC Forms) and the UK Ministry of Justice cloud platform, plus HashiCorp, Google and Azure reference configs. That's 10 repos and 63 root modules with at least 10 resources each, parsed for resource blocks, references, file names and module calls.

95%of AWS, Google and Azure resources have a category in their provider's docs
43%are plumbing: IAM, CloudWatch, logs, secrets and keys
56%share a two-word name stem with a resource of a different type
3%use generic names like this or main
90%live in files other than main.tf, and the file names mean something
91%sit within three reference hops of a root, so graphs are shallow
Signals

How you'd know edge from compute from data

Ranked by how much they help the map, with the evidence for each.

SignalTells youStrengthEvidence
Resource type → provider docs categoryWhat kind of thing it isEvery resource doc page in the AWS, Google and Azure providers has a subcategory: 255 for AWS, 178 for Google, 111 for Azure. For example, aws_db_instance → “RDS (Relational Database)”. A small table maps those to six kinds. Google's “Compute Engine” bucket also holds networks and load balancers, so about 20 type patterns override it.
References and state dependenciesOrder, flow, and what a helper belongs to3,043 in-folder references. State files record each instance's dependencies exactly, across modules. A security group rule points at its group, and the group points at the Redis cluster that uses it.
Shared name stemsWhich resources are one thingIn GOV.UK Chat, chat_redis_cluster names five resources of five types. Prefixes rarely say “edge” or “data”; the common tokens are app parts like notification, api, sms, admin and celery. Region suffixes (_dublin, _london) mark copies of the same thing.
Parent-type prefixesSettings that belong to a parent22% of resources are facets of another resource in the same folder, like aws_s3_bucket_versioning on aws_s3_bucket or aws_iam_role_policy_attachment on a role. These become details on the parent's tile.
File namesThe author's own groupingThe most common files are secrets.tf, cloudwatch_alarms.tf, iam.tf, s3.tf, lambda.tf and rds.tf. Files usually group by service, and sometimes by feature (redis.tf, govgraphsearch.tf). Useful as a tiebreaker and as labels.
count / for_eachCopies to stack33% of resource blocks expand to several instances. One tile with a stack and a count beats twelve identical tiles.
Cross-workspace outputsWhat lives next doortfe_outputs and terraform_remote_state appear in 18 of 133 folders. In GOV.UK they wire 30 workspaces into a clear stack, from vpc up through cluster to apps.
Modules and tagsOwnership and environment429 module calls and 240 files with tags. Module names are good group labels when they exist. Tags vary too much between teams to rely on, but are good filters.

Exploration E

The system map, one level up

Real teams split infrastructure across many workspaces: GOV.UK has 35, and GC Forms has 25 Terragrunt units. Their tfe_outputs links already describe a stack. This is GOV.UK's actual wiring, foundations at the bottom. It belongs in the Library, where you choose which workspace to open.

VerdictStrong, and cheap
It only needs workspace names and their output links, which HCP Terraform already has. No classification needed.
It explains the slices
Chat's missing front door and network make sense here: root-dns and vpc sit two layers below it. Unconnected workspaces (github, ecr, search-api-v2, gcp-gov-graph and others) sit in a side tray.
Recommendation

How the map should work

  • Kind comes from the type, not the name. Ship a table generated at build time from provider docs subcategories (about 540 categories → 6 kinds), plus about 20 type-pattern overrides. Unknown providers fall back to type-name keywords, then to “Other”.
  • Grouping comes from names and references. Fold facets and helpers into the thing they serve, then merge tiles that share a name stem or a same-service reference. Region and AZ suffixes and count/for_each become stacks.
  • Order comes from references. Kind rows run front door to network, and within a row, tiles are placed to minimize crossings. Use state dependencies when there's state, and config references when there isn't.
  • Neighbours come from outputs. tfe_outputs and remote state become ports on the workspace map and edges on a Library-level system map.
  • Never hide anything silently. The supporting shelf and the data sources count account for every resource. List view remains the exact, complete view.
  • Let people correct it. Dragging a resource into a tile, renaming a tile, or moving it to another row is saved per workspace. That turns heuristics into the user's own map without touching code.

The prototype classifier is about 150 lines of Python over raw .tf files. In the app it would run on the state and the provider schemas Habitable already loads, which are more accurate than regex over HCL.
